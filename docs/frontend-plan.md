# Frontend & API Plan — Insurance Policy Assistant

Small phases, Plan → Implement → Validate. The existing ingestion, retrieval and graph
logic is not modified; the API layer only wraps `app` from `src/graph/graph.ts`.

## API contract (v1, minimal)

Base URL: `http://localhost:8080` (dev — Vite proxies `/api` to it).

### `GET /api/health`

`200 { "status": "ok" }` — used by the frontend and any monitoring to check the server.

### `POST /api/ask` — non-streaming answer

Request body (mirrors the graph input):

```json
{ "question": "Am I covered for emergency surgery abroad?", "planCode": "GOLD", "jurisdiction": "FR" }
```

`planCode`/`jurisdiction` are validated as simple uppercase strings; `question` must be a
non-empty string. Optional `treatmentDate` (`YYYY-MM-DD`) may be passed through for
policy-in-force testing; the graph normally sets it itself. Optional `history` (added in
the question-understanding phase; additive — omitting it changes nothing): the previous
turns of the conversation, most recent last, at most 8 entries of
`{ "question": "...", "answer": "..." }`, so follow-up questions like "What is the waiting
period?" resolve against the real previous topic.

Response — an `AnswerResponse` built from the graph's final state:

```json
{
  "status": "answered",            // "answered" | "refused" | "human-review"
  "answer": "...full text...",
  "citations": ["3.1 Emergency treatment..."],
  "confidence": 0.92,
  "revisions": 1,
  "audit": { "verdict": "pass", "issues": [...], "confidence": 0.9 },
  "intent": { "topic": "coverage", "outOfScope": false },
  "policy": { "name": "Gold France 2026", "planCode": "GOLD", "jurisdiction": "FR", "version": "2026.1", "effectiveFrom": "2026-01-01" },
  "sources": [ { "id": "...", "section": "3.1 ...", "content": "...", "score": 0.83 } ],
  "unanswered": []
}
```

Mapping rules (the three known outcomes):

- `final` present → `status: "answered"`. If audit verdict is `reject` on the final draft
  → `status: "human-review"` (answer still shown, never invented — citations empty).
- No `final` and `intent.outOfScope === true` → `status: "refused"` (polite refusal text
  generated by the API layer from the static classifier outcome, not business logic).

Errors: `400` invalid input, `500` graph/database failure with `{ "error": "message" }`.

### `POST /api/ask/stream` — SSE stream of the same run

Same request body (and same validation errors as `/api/ask`, returned as plain JSON with
the matching status code — the stream has not started yet). The stream is built from
`app.stream(input, { streamMode: 'updates' })` and ends with exactly one final event.

Events, in the order the graph produces them:

```
event: stage   data: {"stage":"classify","intent":{"topic":"coverage","outOfScope":false}}
    // v1: since the question-understanding phase the classify intent may also carry
    // non-contractual extras (format, subject, aspects, …). Clients must ignore unknown
    // fields; the two documented fields keep their meaning.
event: stage   data: {"stage":"expand"}
event: stage   data: {"stage":"retrieve"}
event: policy  data: {"policy":{ ...PolicyInfo... }}   // or {"policy":null} — no policy in force
event: stage   data: {"stage":"research"}
event: stage   data: {"stage":"audit","audit":{"verdict":"revise",...}}  // the revise loop:
event: stage   data: {"stage":"research"}           //   returns to research, then
event: stage   data: {"stage":"audit","audit":{"verdict":"pass",...}}    //   passes
event: stage   data: {"stage":"human-review"}       // when the audit sends a draft to a person
event: stage   data: {"stage":"synthesize"}
event: final   data: { ...same AnswerResponse as POST /api/ask... }
```

- `policy` never carries a policy object other than the resolved one or `null`; a `null`
  predicts the human-review outcome. Refused runs end right after `classify`: stage, then
  final with `status:"refused"`.
- `final` is always the last event of a completed run (including refusals and
  human-review). After an `error` event the stream ends with no final.
- `error` data: `{"error":"message"}`.

Client disconnects set a flag checked before every write; the stream closes cleanly and
the server stays up.

No DB writes, no session state: each API call runs a fresh graph invocation from the
request body, exactly like `try-graph.ts` does.

## Building blocks

- `src/api/server.ts` — `node:http` server: routing, JSON body parsing, error handling.
- `src/api/handlers/ask.ts` — runs `app.invoke`, maps state → `AnswerResponse`.
- `src/api/handlers/stream.ts` — runs `app.stream`, converts updates → SSE events.
- `src/api/types.ts` — request/response DTOs shared by the three files above (and later
  imported by the frontend for typing only — no business logic crosses into React).
- `frontend/` — Vite + React 19 + TypeScript + Tailwind, `vite.config.ts` proxies `/api`.

## Phases

### Phase 1 — REST endpoint (non-streaming first)
`node:http` server + `GET /api/health` + `POST /api/ask` with the state→response mapper.
**Validate:** npm typecheck; `curl` health and a real ask (Gold FR → answered; medical
advice → refused; BRONZE → human-review).

### Phase 2 — SSE stream endpoint
`POST /api/ask/stream` using `app.stream` updates; event order verified against the
three known scenarios. **Validate:** `npm typecheck`; `curl -N` showing stage → policy →
final event sequence for each scenario.

### Phase 3 — Frontend scaffold
Vite + React 19 + TS + Tailwind in `frontend/`; dev proxy `/api` → `:8080`; health check
fetch rendered on a bare page. **Validate:** dev server starts; `POST /api/ask` works end
to end from the browser; `npm run build` passes.

### Phase 4 — Chat core (REST, no streaming yet)
Message list, input box, loading and error states, answer rendering with citations and
source sections, policy/version panel, human-review and refused banners. A small typed
API client in the frontend (the only file that knows the wire format).
**Validate:** all three scenarios are visibly distinct in the browser; mobile layout.

### Phase 5 — Streaming + progress UI
Switch the chat to `/api/ask/stream` via `EventSource`-style fetch streaming; stage
progress indicator (including the revise loop), policy card appears as soon as
`event: policy` lands. **Validate:** `npm typecheck`; browser shows progressive stages
and final answer; REST endpoint still works (kept as fallback).

### Phase 6 — Final validation
Both typechecks, graph integration test still green (`npm run test:integration`), full
curl run + browser walkthrough of the three scenarios. No changes to ingestion,
retrieval or graph files.

### Phase 7 — Question understanding & response formatting (backend)
Added `src/graph/understanding.ts` (pure rule layer, `test/understanding.test.ts`): intent
topics (coverage, exclusion, benefits, waiting-period, pre-authorisation, cost,
eligibility, limit, definition, comparison, scenario, summary, source-specific,
missing-information), response formats (direct/list/numbered/short/detailed/summary-N/
table/steps/example/sources, with the only/just/exactly/without-explanation modifiers),
and follow-up resolution (prior subject, quoted previous answer lines, plan/country
change detection). `expand` generates intent-anchored retrieval queries instead of three
fixed ones; `retrieve` searches a second in-force plan for explicit comparisons (same
jurisdiction/date rules); `research` ranks claims by best retrieval score and records
aspects with no evidence as `unanswered`; `synthesize` renders the audited claims in the
requested format and reports missing policy information as missing (never an invented
exclusion). The API gained only an optional additive `history` field, and the chat now
sends it (previous turns, capped at 8, only acts with the same policy). The class of
LLM upgrades to classify/expand/research/synthesize (guide step 4) is unchanged.

### Phase 8 — LLM-powered research, audit and synthesis (guide step 4)

The fake placeholder nodes became real Gemini calls with structured output
(`withStructuredOutput` + Zod schemas from guide B.4), while `classify`/`expand` keep the
Phase 7 rule layer (intent detection and response formats unchanged) and the graph keeps
its shape. `research` answers only from the retrieved chunks and every claim are
code-verified against the chunk it cites (`nodes/quote-check.ts`, guide B.6): anything
unquotable is dropped, and a blank draft degrades to quoting the top-ranked chunks
verbatim rather than returning nothing. `auditDraft` rejects empty drafts with no model
call, merges the model audit with the code checks, forces `revise` when a pass carries
high-severity issues and computes confidence `min(model score, 0.95, solid share)`.
`synthesize` writes the answer from the passed claims only in the requested format;
markers must exist, stay in range and keep print order, shape-critical formats
(N-point summary, one-line short answer) are counted, markers are renumbered to match the
citations array, and any failed check re-renders the same claims with the Phase-7
renderer (`nodes/render.ts`). Missing-information answers keep their deterministic gap
statement. LLM nodes retry with backoff for the free tier's 5-requests-per-minute
throttle, and the chat model is switchable with `CHAT_MODEL` (default `gemini-3.8-flash`,
since the free tier serves only flash-family models). Contracts unchanged; new tests:
`test/llm.test.ts` (quote verification, claim selection, marker checks), marker/citation
alignment in `test/integration`, plus a detailed-explanation and an unsupported-question
scenario in `api:check`.

## Explicitly out of scope for now

- Server-side sessions (context stays client-driven via the optional `history` field).
- Any writes to the database.
- Postman/OpenAPI contract artifacts (happy to add one once Phase 1 is validated).
- Production CORS/hosting concerns.
